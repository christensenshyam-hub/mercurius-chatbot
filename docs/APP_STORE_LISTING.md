Product facts this pack is written against (do not advertise anything else):

- Store name **Mercurius AI**, Education, iPhone + iPad (universal), iOS 17+, free, no
  accounts, no ads, no tracking. Age rating **13+** (forced via the
  minimum-age option).
- Three modes — **Socratic** (default), **Discussion**, **Debate**. There is no
  "Direct" mode any more; do not mention one anywhere.
- A learning path of **8 units / 35 lessons**; lessons stream in beats with
  tappable **KEY IDEA / EXAMPLE / CHECK** cards; the server marks a lesson
  complete when the student demonstrates the objective; unit checks; streaks;
  two opt-in reminders (weekly nudges and a daily streak reminder — local
  notifications, both off until the student turns them on); finished lessons
  and passed units are saved to our server under the session id.
- Photos can be attached to a message and are sent through our server to
  Anthropic's Claude with the message. **All replies are generated by Claude.**
- Built by the **Mayo AI Literacy Club**, a student club.

Wording to avoid everywhere (store, site, reviewer notes): "revolutionizes",
"replaces tutors", "guarantees learning", "eliminates cheating", "the only app
you need", "confidence signal", "stays on your device". Prefer specific,
checkable claims: "guides with questions", "built around verification and
reflection", "responses are generated by Claude".

## 3. App Privacy (the nutrition label)

Must match `ios/Mercurius/Resources/PrivacyInfo.xcprivacy`. If the manifest
and this label ever disagree, review will bounce the build — update both
together.

**Linked = Yes (AUD-57, October 2026 audit).** Apple counts data stored under
a user ID as linked to the user, and everything here is stored under the
session id, so all four rows are **Linked: Yes, Tracking: No**. These App
Privacy answers can be changed in App Store Connect without a new build.
Known gap: build 16's `PrivacyInfo.xcprivacy` still says
`NSPrivacyCollectedDataTypeLinked = false` for these four types; the iOS
batch flips them to `true` for the next build. The audit judged a review
bounce over that mismatch possible but speculative, and advised not to hold
build 16 for it.

**Do you collect data from this app?** Yes.

| Data type (ASC category → type) | Collected | Linked to the user's identity | Used for tracking | Purpose |
|---|---|---|---|---|
| Identifiers → **User ID** (the anonymous session id) | Yes | **Yes** | **No** | App Functionality |
| User Content → **Other User Content** (chat messages, attached-photo captions, reported content) | Yes | **Yes** | **No** | App Functionality |
| User Content → **Photos or Videos** (photos the student attaches to a message) | Yes | **Yes** | **No** | App Functionality |
| Usage Data → **Product Interaction** (finished lessons and passed units synced to our server; lesson start / turn / finish events) | Yes | **Yes** | **No** | App Functionality, Analytics |
| Everything else (contact info, health, financial, location, contacts, browsing/search history, the other usage-data types — advertising data and other usage data — diagnostics, purchases, sensitive info) | No | — | — | — |

- **Tracking:** No. There are no advertising or analytics SDKs, no IDFA use and
  no tracking domains in the privacy manifest. The Analytics purpose on
  Product Interaction is our own lesson events on our own server, which the
  founder reads to see whether the lessons work.
- The label describes what the app sends to **our own server**. The server
  forwards messages and photos to Anthropic to generate replies; the privacy
  policy says so. Nothing is collected before the student agrees on the
  first-launch disclosure screen.
- **Linked: Yes** for all four (AUD-57). Apple counts data kept under a user
  ID as linked to the user, and everything we keep is stored under the
  session id so it can be shown back, synced and deleted. The session id is a
  random string in the Keychain and is never tied to a name, email, phone
  number or Apple ID — none of those are ever asked for. The privacy page says
  the same thing in plain words: "What we keep is filed under a random ID,
  never your name or an account. Usage rows also carry the scrambled network
  address described above." (Not "linked only": the `usage` table stores the
  salted IP hash next to the session id.) The privacy manifest says Linked =
  true from the build after 2.3.0 (16); the App Store Connect answers can be
  changed without a new build.

### 7.2 Screenshots (Mac)

**Sizes:** 16:10, one of **1280 × 800, 1440 × 900, 2560 × 1600 or 2880 × 1800**
pixels, 1 to 10 shots. Ours are **2560 × 1600** (a 1280 × 800-point window on
a Retina display). 2880 × 1800 needs a 1440 × 900-point window, and macOS
won't make a window taller than the screen's visible area: the founder's
14-inch MacBook Pro has 888 points, so it can't be taken there. On a display
with at least 900 points of visible height, `STORE_SIZE=1440x900` gives
2880 × 1800. App Store Connect scales either for display.

**How:** build the `MercuriusMac` scheme (Debug), then from `ios/`:
```bash
scripts/mac-store-screenshots.sh ~/Desktop/mercurius-mac-store
```
It launches the app through the DEBUG `-MacSnapshot` harness, once per
state, isolated (in-memory chats and session id, the local server URL —
nothing reaches production), with the window's rounded
corners filled and no alpha channel. It writes `01-path.png` … `06-chat-thread.png`
and fails on a wrong size, on alpha, or on anything the harness couldn't do.
The app is dark only, so the pictures are dark: the harness still asks for
light, but the windows keep the night look. Retake any set made before
`feat/ios-night-only`, which was light.
**The Mac must be unlocked with the display on**: with the screen locked the
window server draws nothing and the pictures come out blank and the wrong size.
The harness also activates the app for each shot and fails a picture of an
inactive window (grey traffic lights, washed-out sidebar text, grey
prominent buttons), which a locked Mac can't avoid: run it when nobody is
typing on the Mac, since each shot takes the keyboard for a few seconds.

| # | State | What it shows | Caption (if you add a band) |
|---|---|---|---|
| 1 | `path` | Unit 1's stretch of the path in the window, the sidebar with all eight units | *Learn how AI really works — 35 short lessons.* |
| 2 | `lesson` | A lesson reply with KEY IDEA / EXAMPLE cards at the Mac's reading width | *Short lessons. Show you understand.* |
| 3 | `chat` | The empty chat: the toolbar's Socratic / Debate / Discussion picker and the prompt cards | *A tutor that asks — so you actually learn.* |
| 4 | `today` | Today: the next lesson, this week's goal, the streak and recent chats | *Pick up where you left off.* |

| 6 | `chat-thread` | A saved thread (see the caution below) | — |

Check every shot by eye before uploading, at full size:

- **The harness can't draw Liquid Glass.** It photographs only the app's
  window, and glass surfaces blend with whatever is behind the window. The
  sidebar can come out darker than on screen, and the chat toolbar's band can
  show the thread's text behind the mode picker instead of blurring it (it
  does in `chat-thread`). A shot that looks wrong that way is a capture
  artefact; take that one by hand instead (⇧⌘5, "Capture Selected Window",
  with the window at 1280 × 800) — and then flatten its rounded corners and
  shadow, since App Store Connect wants an opaque 16:10 picture.
- **`chat-thread` is a seeded demo** (`-SeedDemoChat`): its replies explain
  directly ("A hallucination is when…") rather than asking, which is not how
  Socratic mode talks. Same rule as §5: real content only. Either replace it
  with a real Socratic exchange or leave it out; the first five don't need it.
- **Fresh state:** every run starts at Lesson 1 with nothing done (`0/4` per
  unit, "This week · 0 of 2"). That is a true picture of a new install, not a
  staged number. A shot with real progress needs a real lesson finished on
  that Mac first, outside the isolated harness.
