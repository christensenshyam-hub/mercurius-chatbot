# Mercurius — Security & Readiness Audit

Read-only pass. Method: six parallel readers (one per fear-area) traced the actual
code, then every P0 and every "this does not exist" claim was handed to a second,
adversarial reader whose job was to **refute** it by re-opening the files. 25 agent
passes, 346 tool calls. Nothing below is inferred from "a good app would have it" —
each line was opened. Paths use the real prefix `ios/Packages/…`.

**Bottom line:** the two things you feared most (P0-1 key extraction, P0-4
crash / dropped message) are **not real in this codebase** — verified clear, with
evidence. The genuine P0s are all in **API spend** and **minors' data**, exactly the
two areas where a school-year push turns a small problem into an unpayable bill or a
COPPA/App-Review problem.

---

## First: the two fears that are actually FINE (verified, not assumed)

### CLEARED — P0-1: The Anthropic key is NOT extractable from the app or the wire
**Evidence:** The iOS app never holds the key. Every outbound request sets only three
non-auth headers — `ios/Packages/NetworkingKit/Sources/APIClient+Chat.swift:94-96`:
```swift
request.setValue("application/json", forHTTPHeaderField: "Content-Type")
request.setValue("text/event-stream", forHTTPHeaderField: "Accept")
request.setValue(UUID().uuidString, forHTTPHeaderField: "x-trace-id")
```
The request body is `{messages, sessionId, responseMode, imageId}` — no secret. The key
lives only on the server (`server.js:116  apiKey: process.env.ANTHROPIC_API_KEY`). Greps
for `sk-ant|ANTHROPIC_API_KEY|x-api-key` across every iOS `.plist/.json/.xcconfig/.entitlements/.yml`
→ **0 hits**; `project.yml` bundles no secret resource. The app talks only to the Railway
relay. The adversarial verifier hunted specifically for a leaked/bundled key and found none.
**Residual (P2, cosmetic):** the SSE error frame forwards the raw SDK `err.message`
(`server.js:1648`) — it never contains the key, but can leak upstream billing/quota text to a
student's screen. Optional 30-min fix: send a static error string there like the 500 path already does (`server.js:1713-1715`).

### CLEARED — P0-4: No crash vector, and the user's typed message is never silently dropped
**Evidence:** Zero crash primitives (`try!`, `as!`, `fatalError`, `[0]`, `.first!`) across the
entire send path (ChatViewModel, ChatView, APIClient+Chat, SSEDataDelegate, SSEParser). The
typed text is appended **and persisted before** the draft clears —
`ios/Packages/ChatFeature/Sources/ChatViewModel.swift:290-294`:
```swift
messages.append(userMessage)
persistMessage(userMessage)
// …
draft = ""
```
Every failure — dropped connection, 4xx/5xx, cancelled stream, malformed frame, empty
reply — funnels through `markCurrentFailed` (`ChatViewModel.swift:1101`) which sets a visible
`.failed` state, rendered at `MessageBubbleView.swift:77`. The server even guards the SDK's
abort-time `Promise.reject` (`server.js:1658`) that would otherwise crash Node on every client
disconnect. An empty upstream reply is backfilled (`server.js:1605`). This path is genuinely robust.
(Two narrow streaming edge cases survive as P2s below — a corrupted frame and a cleanly-truncated
stream — but neither crashes or loses the user's text.)

## P0 — Fix before anyone else installs

### P0-A · No global spend ceiling — cost scales linearly with attacker IPs to an unbounded bill
**Severity:** P0
**Evidence:** No aggregate cap exists anywhere. Grep of `server.js/lib/db.js` for
`spend|budget|daily|cost|quota|cap|circuit-break|kill` returns only per-request token budgets
and gamification XP caps — never a cross-user total. `db.js` has no usage/token/cost table. The
only per-attacker backstop is per-IP: `server.js:1146  chatLimiter 15 req/min`. There is no
counter summing tokens or cost across users/time and refusing calls past a threshold.
**Why it matters:** Nothing stops a fleet of IPs — or your 20 users going viral in a school push —
from driving spend past any budget; cost is `N_IPs × 15/min` with no upper bound and no alert.
Two high-schoolers with no company card cannot absorb the bill that produces.
**Minimum fix:** After each Anthropic call, `INCRBY` an estimated-token counter on a
`rl:spend:YYYY-MM-DD` key (Redis, or in-memory for a single replica); before every Claude call
check it against an env `DAILY_TOKEN_CEILING` and return 503 when exceeded.
**Effort:** 6–10h (most of it wiring the estimate at the 8 call sites).

### P0-B · No kill switch — stopping abuse requires a Railway redeploy
**Severity:** P0
**Evidence:** None of the 8 Anthropic call sites (`server.js:1057, 1096, 1577, 1676, 1822, 2056,
2084, 2115`) is gated by any runtime flag. The full env set (`ADMIN_PASSWORD, ALLOWED_ORIGIN,
ANTHROPIC_API_KEY, DATABASE_URL, GAMIFICATION_ENABLED, IMAGE_STORAGE_DRIVER, LOG_LEVEL,
MEMORY_MODEL, MODEL_ALLOWLIST, NODE_ENV, PORT, REDIS_URL, SQLITE_PATH, STREAK_TZ,
USE_UNIFIED_PROMPT`) contains nothing that disables Claude.
**Why it matters:** When a runaway bill or abuse starts, the only "off switch" is unsetting
`ANTHROPIC_API_KEY` — which triggers a full Railway restart (minutes of continued exposure) and
also wipes the in-memory rate-limiter state. You cannot halt spend from your phone in seconds.
**Minimum fix:** Read an env `CLAUDE_DISABLED` per-request at the top of the chat handler (and the
other Claude routes); return a friendly 503 when set. An admin-toggled Redis flag is better (flips
without restart).
**Effort:** 2–4h.

### P0-C · Minors' chat is stored indefinitely and there is NO code path to delete it
**Severity:** P0
**Evidence:** `db.js:229  INSERT INTO messages (session_id, role, content, timestamp)` stores every
turn a 13–18-year-old types; prod is persistent Postgres (`db.js:6` `USE_PG = !!DATABASE_URL`).
Also stored un-scrubbed: `student_memory` (an LLM-extracted profile of the child — see the "one
thing you didn't ask about" below), raw image bytes, reports. Grep of `server.js` for
`app.delete` → **zero routes**; grep of `db.js` for `delete|purge|DROP|truncate` → **nothing** —
no `deleteSession` helper exists. Yet your own `marketing/privacy.html:170-173` promises:
```html
Email us for full deletion … We'll process the deletion within 30 days.
```
**Why it matters:** The publicly-promised 30-day deletion right cannot be honored except by two
teenagers hand-running SQL — not auditable, not reliable. A parent, school, or App Review reviewer
asking "how do I delete my child's transcripts" has no defensible answer, and the schema
contradicts "we do not knowingly retain."
**Minimum fix:** Add a `deleteSession(sessionId)` helper that deletes from messages,
student_memory, images, reports, sessions in one transaction, and expose an authenticated
`DELETE /api/session/:sessionId` keyed to the caller's own id.
**Effort:** 6h.

### P0-D · The web widget collects a minor's name and publishes it on an unauthenticated public leaderboard — contradicting your own "No name" privacy policy
**Severity:** P0
**Evidence:** `public/widget.js:538` prompts "Add your name so we can personalize…" →
`widget.js:382  body: JSON.stringify({ sessionId, displayName: name })` →
`server.js:2167` stores it (regex allows spaces → full "First Last") → `GET /api/leaderboard`
(`server.js:1876`, **no auth**) returns `name: r.display_name` (`db.js:380`) to any caller.
This flatly contradicts `marketing/privacy.html:104  "No name, email, phone number, or address."`
and the iOS `PrivacyInfo.xcprivacy` (declares no Name data type).
**Why it matters:** A named minor's identity + streak/activity is served to any stranger on an open
endpoint — the exact opposite of your privacy page's headline. It's a one-minute, checkable
contradiction a parent or App Review will catch. (The iOS app's leaderboard was removed this cycle,
but the widget UI and the live `/api/profile` + `/api/leaderboard` endpoints still do this.)
**Minimum fix:** Cheapest defensible: drop `name` from `db.js:380` `getLeaderboard` output and
remove the "Add your name" prompt in both `public/widget.js` and `mayo-site/widget.js`. Or gate it
behind real disclosure and correct `privacy.html`.
**Effort:** 3h.

### P0-E · No age gate, birthday, or parental-consent mechanism anywhere (COPPA exposure)
**Severity:** P0
**Evidence:** Grep for `coppa|parental|consent|birthday|age|under 13|minor` across server, db, lib,
all iOS Swift, and both widgets returns only curriculum prose, marketing copy, and doc assertions
(`ios/docs/APP_STORE.md:144` "We do not knowingly collect … from children under 13"). The only
iOS "gate" is `AppEntryView.swift:46  @AppStorage(…hasSeenOnboarding)` — a tutorial-seen flag; the
sole onboarding checkbox is an AI-fallibility disclaimer, not age or consent. No birthday field, no
consent flow, no age parameter on any route.
**Why it matters:** The app is aimed at high-schoolers, its userbase is majority minors, and it's
pushing into schools where under-13 exposure is likely — yet nothing screens age before a child
starts sending chat stored forever (P0-C) and, on the widget, a name (P0-D). "We do not knowingly
collect from under 13" is an unenforceable assertion, not a control — the classic COPPA/App-Review
failure mode.
**Minimum fix:** A one-time "you must be 13+" neutral age screen in the iOS doorman and the widget
before first chat; keep out of Apple's Kids Category (already advised in your own listing doc);
document a school/parent consent path for the rollout.
**Effort:** 6h.

**Related P1 (was flagged P0, verifier downgraded):** "Start Over" (`SettingsViewModel.swift:151`
→ `SessionIdentity.reset()`, keychain-delete only, no network call) rotates the local id but leaves
all server data **orphaned** — and because it destroys the session id, even the email-deletion path
(which requires quoting your id, `privacy.html:171`) becomes permanently impossible for pre-reset
data. Fix folds into P0-C: call `DELETE /api/session/:id` with the current id *before* rotating. 3h.

## P1 — Fix before the school-year push (maps to your P1 list)

**Instrumentation — you are flying blind on all five metrics you named.** Each verified as a genuine absence:

- **API cost per user — NOT MEASURABLE.** `grep '\.usage' server.js db.js lib/` → nothing; every
  Anthropic call ignores the returned token counts. `lib/metrics.js:48-103` has no `*_tokens_total`
  or cost counter. You cannot answer "which user cost us $40 yesterday." *Fix: read `message.usage`
  off each response, increment a `anthropic_tokens_total` counter + a per-session `usage` table. 4–6h.*
- **Crash-free session rate — NOT MEASURABLE.** No crash SDK and no MetricKit subscriber
  (`grep Crashlytics|Sentry|Firebase|MetricKit|MXMetricManager` over all iOS → 0). The only sink is
  `OnboardingTelemetry.swift:4` — "Local-only OSLog … Nothing leaves the device." No numerator, no
  denominator. *Fix: register an `MXMetricManagerSubscriber` (zero-SDK) and POST `{sessionCount, crashCount}`. 6–10h.*
- **Lesson completions — COMPUTED THEN DISCARDED.** `lib/lessonOutcome.js:37` derives
  `lessonComplete`, strips the marker from the saved reply, forwards the boolean to the client
  (`server.js:1634/1707`) — and never counts or persists it. Your core efficacy KPI is dropped on
  the floor. *Fix: on completion, increment `lesson_completions_total{unit}` and insert a
  `lesson_events` row parsed from the `[CURRICULUM:]` tag. 3–5h.*
- **D1/D7 retention — NOT INSTRUMENTED.** `db.js:384 getDashboardStats()` computes totals/unlock
  rate/top topics but no cohort/retention; the sessions row has one `last_active`, not per-day
  activity. Answering "what % who started Monday came back" needs hand-written SQL every time.
  *Fix: nightly cohort job over `messages.timestamp`; surface D1/D7. 4–8h.*
- **Lesson starts — NOT RECORDED (P2).** The messages schema is `(session_id, role, content,
  timestamp)` only; a lesson-start turn is indistinguishable in storage, so completions have no
  start-denominator for a funnel. *Fix: same `lesson_events` table, `event='start'`. 2–3h.*

**Prompt — the core IP is untested and its prod version is unverifiable.**
- **Zero behavioral/injection tests (P1).** `grep tests/ for unifiedPrompt|mercurius-v2` → empty.
  The only "prompt tests" (`tests/responseQuality.test.js:50`) assert substrings of the **legacy**
  `MODE_RULES.socratic` string that's only used when `USE_UNIFIED_PROMPT` is OFF, and send nothing
  to Claude. No test feeds a jailbreak and asserts refusal. Any edit to the 26KB prompt (or the
  injection block) can regress with a fully-green `npm test`. *Fix: an eval suite that sends
  canonical "write my essay" / jailbreak / "invent a citation" inputs through the real assembly and
  asserts non-compliance. 6–12h.*
- **Injection mitigation is prose-only and structurally weak (P1).** The defense exists only as
  prompt text (`prompts/mercurius-v2.md:701`). The user turn is injected raw:
  `server.js:1538  {role:'user', content: latestContent}` with no delimiter marking untrusted text.
  A student's "ignore your rules" is mitigated only by model compliance, not architecture. *Fix:
  wrap the user turn in a `<user_message>…</user_message>` block the system prompt treats as data. 3–6h.*

**Gamification / content integrity.**
- **Curriculum progress is client-only and wiped on reinstall (P1).**
  `ios/Packages/CurriculumFeature/Sources/ProgressStore.swift:52-57` backs completed lessons +
  mastered units with `UserDefaultsPreferenceStore` only; `db.js` has no curriculum table; there is
  no server restore path. A teen who reinstalls / gets a new phone keeps their **streak** (server,
  Keychain-keyed) but loses **100% of learning-path progress** — every lesson re-locks, every
  "Mastered" badge vanishes, unrecoverable (no accounts). *Fix: persist completion server-side keyed
  by the existing session id and seed the store from a GET on launch, mirroring `StreakStore.seed`.
  8–16h.* (Note: a flag-gated `xp_ledger` path does record completed ids, but it's disabled in the
  shipped build and never read back to restore.)
- **Session rate-limit is trivially bypassable (P1).** `server.js:1202` keys the 20/min bucket on
  the request-body `sessionId` (`lib/rateLimiter.js:218`), which is an unauthenticated
  client-chosen string. Rotate a random id per request and it never trips — only per-IP (15/min)
  actually constrains one attacker, and each chat turn fires a **second** (memory-extraction) Claude
  call (`server.js:1057`), doubling per-request cost. *Fix: bind the bucket to `IP+sessionId`, lower
  `chatLimiter`, and add the P0-A global ceiling. 2–4h.*

**Content depth — the runway is ~2 weeks, not a school year (P1).**
`ios/Packages/CurriculumFeature/Sources/Curriculum.swift:96-371` defines exactly **8 units, 35
lessons** (units 1–5 × 4, units 6–8 × 5; `grep -c "Lesson(" = 35`) plus 8 unit tests. At a realistic
4–5 lessons/sitting the entire structured path is exhausted in **~7–9 sittings (~1.5–2 weeks)**;
after that it's open Socratic chat with no new gated content. *Fix: this is authoring, not code —
tasks #80/#81 ("deepen units 1–5", "full content review") are still pending, confirming it's
known-but-unfinished. 40+h.*

## The three things to fix before anyone else installs

1. **Spend cap + kill switch (P0-A, P0-B).** These are the difference between a viral
   school-year push being a win and being a bill two high-schoolers cannot pay, with no way to stop
   it from your phone. ~1–1.5 days for both.
2. **Age gate + kill the real-name public leaderboard (P0-E, P0-D).** A neutral 13+ screen and
   removing the named-minor public endpoint close the two COPPA/App-Review contradictions a parent
   or reviewer catches in one minute — and one of them (the leaderboard) directly contradicts your
   own published privacy page. ~1 day.
3. **A real deletion path (P0-C, + the Start-Over fix).** Turn the written "30-day deletion"
   promise into an actual `DELETE /api/session/:id` and wire "Start Over" to call it before rotating
   the id. Until this exists, the promise on your privacy page is false. ~1 day.

Everything you feared as P0-1 (key) and P0-4 (crash) is genuinely handled — spend your P0 hours on
the two areas above, not on the two you led with.

## The one thing you did not ask about, and should worry about most

**Every chat turn secretly fires a *second* Claude call that builds and permanently stores an
AI-inferred psychological/academic profile of the minor** — `server.js:1057`
`extractAndSaveMemories → anthropic.messages.create` (MEMORY_MODEL) writes interest/struggle/insight
items to a `student_memory` table (`db.js:449`), keyed to the child, with no deletion path and no
mention on your privacy page. This is worse than "we store chat": it's an *inferred profile of a
named/session'd 13-year-old* — the most sensitive category of data you hold — and it **doubles your
per-message API cost**, which quietly breaks the spend math behind every rate-limit number in this
audit. It sits at the intersection of all three of your top fears (cost, minors' data, and the
promises on your privacy page) and it's the one you didn't name. Decide deliberately whether you
need it at all; if you keep it, it must be disclosed and deletable.

## What I could not determine from the code, and what I'd need

Three load-bearing facts live in the **Railway runtime environment**, not the repo, and change the
severity of findings above — I could not verify them statically:

1. **Which database driver is live in prod.** `db.js:6` selects Postgres iff `DATABASE_URL` is set,
   else SQLite on Railway's ephemeral disk. If it's SQLite, "indefinite retention" (P0-C) is
   actually *data-loss-on-redeploy* — a different problem, and it means your retention analytics
   (P1) have silent gaps. **Need:** the Railway variable list showing `DATABASE_URL`.
2. **Whether `USE_UNIFIED_PROMPT` is set in prod.** It defaults OFF and is absent from
   `.env.example`. If unset, the injection-hardened v2 prompt — the only place the
   `<prompt_injection_defense>` block exists — is **not being served to students**; the thinner
   legacy path is. **Need:** the prod value of `USE_UNIFIED_PROMPT`.
3. **Whether `STREAK_TZ` and `GAMIFICATION_ENABLED` are set.** These decide whether streaks roll
   over at the right local time and whether the (farmable, dual-calendar) gamification paths are
   even live. **Need:** those two prod values.

A screenshot of the Railway Variables tab answers all three in one look.
