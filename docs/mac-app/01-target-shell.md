## What was built

**The target (`ios/project.yml`)**
- `MercuriusMac`: a macOS 14 `application`, scheme `MercuriusMac`, product `Mercurius.app`, module `MercuriusMac`.
- Release builds use `com.mayoailiteracy.mercurius.native`, the iOS id, for the universal purchase. Release signs manually with Apple Distribution and a "Mercurius Mac App Store" profile, which doesn't exist yet (release step).
- Debug builds use `com.mayoailiteracy.mercurius.native.macdev`, signed Automatic / Apple Development (team TMBPRHZYW2). The reason: this Mac has an iPad build of Mercurius installed (`/Applications/Mercurius.app`, same bundle id), and its data lives in `~/Library/Containers/com.mayoailiteracy.mercurius.native`. A Debug build with the same id would share that container. See PLAN.md.
- Entitlements (generated by xcodegen into `MercuriusMac/MercuriusMac.entitlements`): App Sandbox, network client, user-selected files read-only (attaching a photo). Hardened runtime is on.
- Info.plist (generated): the same answers as iOS (encryption exemption, strict ATS, education category, `mercurius://` scheme), plus `LSMinimumSystemVersion`.
- Icon: `MacAppIcon`, all ten macOS sizes. `ios/scripts/make-mac-icon.py` builds it from the iOS 1024 px icon: the art on an 824 px rounded plate in a 1024 px canvas with a soft shadow, per Apple's macOS grid.
- The shared `Mercurius/Resources/Assets.xcassets` (logos, colours) and `PrivacyInfo.xcprivacy` are referenced, not copied. The built app's `Assets.car` holds AccentColor, LaunchBackground, LogoHero, LogoIcon, LogoIconDark and MacAppIcon, and none of the iOS AppIcon.
- The xattr-strip build phase is included, as on every target.

**The app (`ios/MercuriusMac/App`)**
- `MercuriusMacApp` contains:
  - `WindowGroup` with `RootView`, min 860×600, default 1180×800;
  - `.commands { MacCommands }`;
  - a `Settings` scene (`MacSettingsView`).
- `MacAppDelegate` only starts the DEBUG snapshot harness. The notification delegate isn't installed: reminders are the notifications step.

**The window (`ios/Packages/AppFeature/Sources/Mac`, all `#if os(macOS)`)**
- `RootView` runs the same bootstrap on both platforms. On the Mac it skips the 1.2 s welcome hold and the cold-launch resume.
- `AppEntryView` runs the same gate decision, reminder re-plan and consent withdrawal. On the Mac it mounts `MacShellView` and passes it the same `OnboardingFlow` while the gate shows. On iOS the flow was only extracted into a property; the paths are unchanged.
- `MacShellView` is a `NavigationSplitView`.
  - **The sidebar:**
    - Today;
    - Learning path, one row per unit with done/total and a seal once mastered;
    - Chats: New Chat, then the saved threads, with Delete Chat… behind a confirmation in the context menu.
  - **The detail column** hosts the iPhone's views:
    - `HomeView` as Today (its weekly-nudge card hidden until the Mac schedules reminders);
    - `CurriculumView` filtered to one unit (new optional `unitId`);
    - `ChatView` on the one shared chat model;
    - `CurriculumLessonView`, `UnitTestView`;
    - the gate, centred at 720 pt max width.
  - **Completion bookkeeping** matches `AppShellView`: mark in progress, complete or mastered, the Explorer and Unit Master achievements, and the gamification event (inert while gamification is off). It leaves out the Live Activity (iOS-only) and the review prompt (not on the Mac yet).
- `MacShellModel`, owned by `AppEnvironment`, holds the selection, the open lesson or check, and the one `ChatViewModel`, which is built on first use. It also exposes the guarded actions the menu uses. It is shared by the window, the menu bar and the Settings window.
- `MacCommands`:
  - File ▸ New Chat ⌘N, which replaces New Window (the app is one window);
  - View ▸ Today ⌘1, Learning Path ⌘2, Chat ⌘3;
  - the standard sidebar commands.
  - All are disabled while the gate shows.
- `MacSettingsView` (⌘,) is the iOS `SettingsSheet` (theme, privacy choices, delete my data, withdraw consent), wired to the window. A reset re-reads the sidebar's chats (new `SettingsSheet.afterReset`). Withdrawing consent puts the window back on the gate, and records the withdrawal itself in case the window is closed. Before consent is on record it shows only a pointer to the main window.

**No network before consent.** While the gate shows:
- the detail column *is* the gate;
- the sidebar is collapsed, its toggle removed and the column disabled;
- every menu command is a no-op (`isGated`);
- the Settings window is a placeholder;
- the shell's server tasks (`progressSync.pullOnLaunch`, the Progress hub) run only in `.task(id: isGated)` once it is false;
- the chat model isn't built.

Bootstrap fetches only when consent is already current, as on iOS. `MacShellModelTests` pins the gating.

**DEBUG launch arguments (Mac).** The gate still comes first, as on iOS:
- `-EnterShell` opens Today;
- `-EnterShellCurriculum` opens the next stop's unit;
- `-LessonPreview` opens Unit 1 Lesson 1 in the detail column; add `-LessonReplay` for the recorded replies (no network) and `-LessonSkipIntro` to start straight away;
- `-ChatPreview` opens the chat;
- `-GateStep <step>` and `-consentVersion` / `-hasSeenOnboarding` (argument domain) work as on iOS.

New for screenshot runs:
- `-EphemeralSession` keeps the session id in memory, so no Keychain item is touched;
- `-UseLocalServer` already existed.

## The screenshot harness: `-MacSnapshot <dir>`

`MercuriusMac/App/MacSnapshot.swift` (DEBUG) renders the app's own window to a PNG, writes it and quits. `ios/scripts/mac-snapshots.sh <dir> [shot…]` runs the set, each in isolation: `-UITests YES` (in-memory chats), `-EphemeralSession YES` and `-UseLocalServer YES`, so nothing reaches production.

What actually worked, and what didn't:
- **`cacheDisplay` and `ImageRenderer` don't work here.** `NSView.cacheDisplay` (and `CALayer.render(in:)`) on macOS 26 draws the window chrome around **blank** content: SwiftUI renders through Metal-backed layers those can't read. `ImageRenderer` can't draw the AppKit-backed lists and scroll views. So the harness asks the window server for **its own window's image**: `CGWindowListCreateImage` with `.optionIncludingWindow`, looked up at run time because the macOS 15 SDK marks it obsoleted. That needs no Screen Recording permission for the caller's own windows. `CGPreflightScreenCaptureAccess()` returned false on this Mac, the capture still worked, and tccd logged no screen-capture request. `cacheDisplay` remains the fallback.
- **Liquid Glass doesn't survive the capture.** Surfaces that blend with what's behind the window come out **dark** (the sidebar, a toolbar's scroll-edge band, the composer's text field) or **missing** (the consent checkbox's and the age pop-up's bezels). This is a capture artefact: `-MacSnapshotDumpControls YES` lists the window's AppKit controls, and the consent step's 16×16 checkbox is there at the card's trailing edge (`gate-consent.controls.txt`). On-screen appearance of those controls has **not** been checked by eye; that's in step 2.
- **Give every flag a value** (`-EnterShell YES`). With `-EnterShell -MacSnapshotDelay 9`, AppKit took the bare `9` as a document to open, and SwiftUI then opened no window at all.
- **The window is moved almost entirely off screen** before it is first drawn, and never activated, so a run barely shows and never takes the keyboard. Early runs were centred on screen; someone on this Mac clicked their close buttons (a `willClose` trace showed a real mouse click on the close button), which is why some early shots failed.
- The sandbox refused `/private/tmp`, so the harness falls back to the container's tmp and says where it wrote. Writing into the repo under `~/Desktop` was allowed.

**Found and fixed while looking at the shots**
- **No dark mode on the Mac.** `BrandColor`'s adaptive tokens returned the light value on every non-UIKit platform. They now use an `NSColor` dynamic provider, and `today-dark.png` is the proof. `BrandLogo` also gets its logo assets on the Mac now (it used to fall back to the drawn mark).
- **The sidebar opened at 148 pt**, truncating every unit title, once `.toolbar(removing:)` sat outside `navigationSplitViewColumnWidth`. The column width is now the outermost modifier, and the window opens at 250 pt, after the gate too.
- **The sidebar toggle showed during the gate.** `.toolbar(removing: .sidebarToggle)` only takes effect on the sidebar column.

**Seen, left for later steps**
- The composer's text field draws as a dark bar inside its capsule. That's the macOS text-field bezel and/or the glass capture; step 3.
- Message bubbles keep their phone width in a wide window (step 3). The path-side Merc stands at the window's edge, far from the frontier node (step 5).
- The window title (Today, the lesson's title, "Welcome to Mercurius") is set. In an inactive window it is drawn very faintly, and on light shots it is hard to see.

## Tests

- `swift test` (macOS host): **937 tests in 139 suites, all pass**. Before this step it was 927 in 138; the new ones are `MacShellModelTests` (9) and `SettingsResetTests.afterResetRunsLast` (1).
- The Mac app builds (Debug, Xcode 26.4) with no warnings from the new code.
- iOS: `build-for-testing` of the `Mercurius` scheme (app, widgets, unit and UI tests) succeeds. UI-test anchors: on iPhone 16 (iOS 26.4) I ran `testBootCompletes`, `testTabBarHasChatAndCurriculum`, `testChatHeaderExposesHomeButton` (the Home/Settings header), `testModeSelectorExposesAllModes` (the Debate pill), `testTappingSettingsOpensSheetWithAppearanceSection`, `testHomeShowsNextStop`, `testFirstRunGateLandsInFirstLesson`, `testConsentSentenceTogglesTheSwitch`, `testExistingInstallSeesGateOnceThenHome`, `testUnderThirteenIsBlocked` and `testNotNowPausesAndReviewReturns`. All pass. One exception: `testExistingInstallSeesGateOnceThenHome` failed once, as the first gate test of the first batch (Home didn't appear within 15 s of "Got it"). It then passed on 4 straight re-runs (1 + `-test-iterations 3`) on the same build. I read that as a flake, not a regression. The iOS code path through `AppEntryView` only had the flow extracted into a property. The full UI suite and the snapshot tests weren't run.
- `ArchitectureTests` are unchanged and pass. The Mac window lives in the composition root (AppFeature), so the package graph didn't change; `Package.swift` only had its comment corrected (it said the app ships for iOS only).
- **Not built in CI yet:** the `MercuriusMac` target itself, on Xcode 16.2. The Mac code in AppFeature is compiled by CI's `swift test`. A CI job for the Mac target is in the release step.

## Skipped, and why

- **Snapshot record runs:** none, as the rules require.
- **Reminders on the Mac:** NotificationScheduler/Router are iOS-only. On the Mac, the Your path reminder choice is stored but schedules nothing, and Today hides the weekly-nudge card. → step 4.
- **Crisis numbers as selectable text, a Mac entry point for reporting a reply, the age step's "wheel" VoiceOver hint** → step 2 (safety parity).
- **Mac-native chat polish:** the composer's field style, Return to send, message width → step 3.
- **The App Store review prompt and the Live Activity:** not on the Mac (the second is iOS-only).
- **`X-Mercurius-Client` header:** recommended, not added (PLAN.md, Client identification).
- **Cross-device sync:** out of scope; a product gap (PLAN.md).
